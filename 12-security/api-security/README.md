# API Security

`[INTERMEDIATE]` · Most API breaches are not clever. They are an endpoint that checked you were logged in and never checked the record belonged to you. **Authorise the object, not the route.**

---

## 1. One-line definition

The controls that keep an API correct when the caller is hostile: authorising every **object**
access, validating every input on the server, limiting what any one caller can consume, and keeping
credentials out of places they can leak from.

## 2. Explain like I'm new

A hotel gives you a key card. The card proves you are a guest — that is
[authentication](../authentication/).

Now imagine the door locks only check "is this a guest card?" and not "is this *room 412's* card?".
Every control works exactly as designed. The cards are unforgeable, the readers are fast, the audit
log is complete. And every guest can open every room.

That is the shape of nearly every serious API vulnerability. Not a broken lock — a lock asking the
wrong question. An API endpoint like `GET /api/invoices/8842` that verifies your token and then
returns invoice 8842 to whoever asked has exactly this bug, and changing the number is the entire
exploit.

## 3. Real-world analogy

An office building: badge at the entrance, locks on the individual doors, someone on reception who
notices unfamiliar faces.

**Where it breaks:** physical buildings have a natural limit on doors and a corridor full of people
who would notice you trying every handle. An API has thousands of doors generated by code, no
corridor, and nobody watching — an attacker can try a hundred thousand handles in a minute, from a
laptop, silently, and the only trace is a shape in a metrics dashboard that nobody has alerted on.
The physical analogy also implies effort scales with the number of doors. In software the attacker
writes one loop.

## 4. Technical explanation

### The three questions, in order

| # | Question | Mechanism | Where it is checked |
|---|---|---|---|
| 1 | Who is calling? | [Authentication](../authentication/) | Middleware, once per request |
| 2 | May this caller use this **operation**? | Function-level authorisation | Route middleware — fine here |
| 3 | May this caller use this operation on **this object**? | **Object-level authorisation** | **Only where the object is loaded** |

**Question 3 is the one that gets missed, and it is the one attackers use.** It is called IDOR
(insecure direct object reference) or, in the OWASP API Security Top 10, API1: Broken Object Level
Authorization — first on that list because it is first in reality. Question 2 can be answered by a
gateway or a decorator. Question 3 cannot, because nothing outside the data layer knows which object
the request will touch.

### Authorisation models

| Model | Decision based on | Fits | Breaks when |
|---|---|---|---|
| **ACL** | A list attached to each object | Small systems, explicit per-object sharing | List management at scale; no way to reason about "who can see X" globally |
| **RBAC** | The caller's role | Org-shaped permissions; easy to explain | Role explosion (`editor_eu_readonly_beta`); per-object rules do not fit at all |
| **ABAC** | Attributes of subject, object, environment | Contextual rules — time, location, data classification | Hard to test, hard to reason about, easy to make slow |
| **ReBAC** | A graph of relationships: user → relation → object | Sharing and nesting — documents, folders, teams | Needs real infrastructure (Zanzibar-style) |

Pick the simplest that expresses your rules. **But the model matters far less than where the check
happens** — a perfect RBAC configuration evaluated only at the route is still broken object-level
authorisation.

### Make the check unbypassable

The dangerous pattern and its fix are three lines apart:

```
# Broken — loads first, and the check is one forgotten line away from absent
order = Order.find(params[:id])
render order

# Better — the query IS the authorisation; a missing scope returns nothing
order = current_user.orders.find(params[:id])

# Best at scale — a policy layer the data path cannot skip
order = authorise!(current_user, :read, Order.find(params[:id]))
```

**Design so that forgetting the check fails closed.** Scoped queries, row-level security in the
database, a repository layer that requires a subject argument, a policy object per resource — all of
these turn "someone forgot" from a silent data leak into an empty result or an exception. Relying on
every developer remembering an `if` statement on every endpoint forever is not a control; it is a
hope with a code review attached.

And a warning that saves an argument later: **UUIDs are not authorisation.** Unguessable identifiers
raise the cost of *enumeration*; they do nothing about a leaked, logged, shared, or referred
identifier. Unguessable is not the same as unauthorised.

### The rest of the object-level family

| Vulnerability | What it looks like | Fix |
|---|---|---|
| **Mass assignment** | `user.update(request.body)` lets a caller set `is_admin` or `account_id` | Allowlist the writable fields. Never denylist — the next field added is exposed by default. |
| **Excessive data exposure** | Return the whole record; the front end hides three fields | Serialise explicitly, per audience. **The client is not a filter.** |
| **Broken function-level authz** | `/admin/*` protected in the UI but not on the server | Deny by default at the router; require an explicit policy per route |
| **Object property level authz** | The caller may edit the order, but not its `status` or `price` | Authorise fields, not just records |

### Input validation

Validate on the **server**, always, at the boundary, with an **allowlist** of shapes: type, range,
length, format, enum membership. Client-side validation is user experience, never a control — the
client runs on the attacker's machine, and `curl` does not run your JavaScript at all.

Then the nuance that gets missed: **validation is not the fix for injection.** Injection is a
context problem, fixed by using the right construct for the context.

| Threat | The actual fix | Not the fix |
|---|---|---|
| SQL injection | Parameterised queries / prepared statements | Escaping quotes, "blocking bad words" |
| Cross-site scripting | Context-correct output encoding, plus CSP | Input filtering alone |
| Command injection | Do not build shell strings; pass argument arrays | Quoting |
| Path traversal | Resolve, then verify the result is inside the allowed root | Stripping `../` (trivially bypassed) |
| Deserialisation | Do not deserialise untrusted data into arbitrary types | A denylist of dangerous classes |
| **SSRF** | Allowlist destination hosts; block private and link-local ranges including `169.254.169.254`; re-validate after every redirect | Checking the URL once before following redirects |
| ReDoS | Bounded, reviewed regexes; input length limits; timeouts | Hoping |

SSRF deserves the emphasis: in cloud environments the metadata endpoint hands out credentials to
anything that can make a local HTTP request, so a "fetch this URL for me" feature is a credential
exfiltration primitive unless it is locked down. Beware DNS rebinding — a hostname that resolves to
a public address at validation time and a private one when the request is made.

### CORS is not access control

**CORS is a rule that a browser applies to scripts it is running. It is not enforced anywhere else,
and it grants nothing on your server.** This is misunderstood so consistently that it is worth
stating as a table:

| Belief | Reality |
|---|---|
| "CORS protects my API" | It restricts *browser JavaScript on other origins* from reading responses. `curl`, Postman, a mobile app and a server-side script ignore it entirely. |
| "`Allow-Origin: *` exposes my data" | Not by itself. It cannot be combined with credentials, so it exposes only what an unauthenticated caller could already fetch. Missing authorisation exposes data. |
| "Locking down CORS secures the endpoint" | It secures nothing on the server. It protects *other sites' users* from having your API read with their cookies. |
| "A CORS error means I am blocked" | It means the browser refused to show the response to the script. The request may well have executed on your server. |

The genuinely dangerous configuration is **reflecting the `Origin` header back in
`Access-Control-Allow-Origin` together with `Access-Control-Allow-Credentials: true`**. That
combination lets any website in the world make authenticated requests as your logged-in users and
read the responses. It is usually introduced by someone trying to "fix" a CORS error quickly.

### Rate limiting as a security control

Rate limiting is discussed as a capacity tool; it is at least as important as an abuse control. It
is the defence against brute force, credential stuffing, enumeration, scraping, and the cost attacks
in [DDoS](../ddos/) — with one hard boundary: **it is an L7 control and does nothing against
volumetric traffic that saturates your network before your code runs.**

| Dimension | Stops | Weakness |
|---|---|---|
| Per IP | Casual scanners, single-source floods | NAT punishes real users; IPv6 and botnets rotate addresses freely |
| **Per account / API key** | Credential attacks, scraping, abusive tenants | Requires the request to be authenticated first |
| Per endpoint | Protects the expensive operations specifically | Needs per-endpoint tuning that drifts |
| **Per cost unit** (weighted) | Reflects reality: one search is not one login | More work to implement — and worth it |
| Global | Last-resort self-preservation | Blunt; punishes everybody equally |

Use several together, always return `429` with `Retry-After`, and count *rejections* as a
first-class metric. See the [working rate limiter](../../18-implementations/rate-limiter/) for
algorithms and measured behaviour.

### Secrets

| Where | Verdict |
|---|---|
| In the repository | **Never.** Git history is permanent; deleting the line changes nothing. |
| In a config file on disk | Better than the repo, worse than everything else. Ends up in backups and images. |
| Environment variables | Common and acceptable. Visible in process listings, crash dumps, and error reporters. |
| **Secret manager, short-lived dynamic credentials** | The real answer. Credentials that expire on their own cannot be leaked for long. |
| Workload identity / mTLS | Better still: no shared secret exists to leak |

Three rules, and the middle one is the one people invert:

1. **A committed secret is compromised the moment it is pushed**, including to a private repository.
   Rotate it. Do not merely remove the line — the object stays in history, in every clone, and in
   any fork.
2. **Rotation speed matters more than secret complexity.** A 64-character key you cannot rotate
   inside a week is far more dangerous than a 32-character key you can rotate in five minutes.
   Entropy stopped being the limiting factor decades ago; blast radius and time-to-rotate did not.
3. **The incident is not the leak. It is the leak you cannot revoke.** If your answer to "this key
   is on Pastebin" is a coordinated release across nine services, you do not have a secrets problem
   — you have a *rotation* problem, and you will discover it at the worst possible moment.

Make rotation routine so it is boring: automate it, run it on a schedule, and support two valid
credentials at once so rotation never requires a synchronised restart. Add scanning at commit time
and provider-side push protection, because the cheapest leak to handle is the one that never lands.

## 5. Engineering at scale

**Object-level authorisation becomes a distributed systems problem the moment you have list
endpoints.** One check per object is fine for `GET /orders/8842`; a page of 100 results means 100
decisions, and a naive implementation makes 100 policy calls. Two consequences:

- Batch the interface: `can(subject, action, [objects])`, one round trip.
- Prefer **filter in the query** to *fetch then filter*. Fetching then filtering either leaks
  information through counts and pagination (`page 3 of 40` when you can see nine rows) or forces
  you to over-fetch to fill a page, which is slow and unbounded.

A central policy service — the Zanzibar shape — solves consistency and gives you one place to reason
about access, at the cost of a network hop on every read. So you cache decisions. And caching a
decision means **a revoked share stays live for the length of the TTL** — the identical trade to a
[JWT's revocation window](../jwt/) and to any [cache](../../04-caching/fundamentals/). State the
window; do not discover it.

**A gateway cannot do object-level authorisation, and its presence makes teams believe it does.**
An API gateway is excellent at TLS, authentication, schema validation, coarse route policy and rate
limiting — all the things that can be decided from the request alone. It cannot decide whether
invoice 8842 belongs to you, because it does not know what invoice 8842 is. Services behind a
gateway must not treat their input as trusted: internal callers are compromised in the interesting
incidents, which is the whole argument for mTLS between services and for authorising internal calls
too.

Finally, an organisational control that outperforms most technical ones: **make "has an authorisation
policy" a property the framework enforces**, so a new endpoint without one fails a test rather than
shipping. The most common way a well-designed system develops an IDOR is a new endpoint added in a
hurry by someone who did not know the convention.

## 6. The problem it solves

Everything a system assumes when it trusts its caller. Once an API is reachable, the caller is
hostile by default, the network is not a boundary, the client is attacker-controlled, and every
parameter is an input to an exploit until proven otherwise.

## 7. The problem it does NOT solve

- **It does not fix a bad data model.** If ownership is ambiguous in your schema, no policy layer
  can compute a correct answer — it will faithfully enforce the ambiguity.
- **A WAF does not fix injection.** It is a speed bump that buys time to patch, and it is bypassable.
  Parameterised queries fix injection.
- **CORS does not gate access.** See above. It is a browser policy.
- **Rate limiting does not stop a distributed volumetric attack.** See [DDoS](../ddos/).
- **Perimeter security does not protect against a compromised internal service.** If everything
  inside trusts everything else, one foothold is total. That is what zero trust and mTLS address.
- **None of it stops a legitimate user doing legitimate damage.** Authorisation is not intent
  detection; that is audit logging, anomaly detection, and approval workflows.

## 9. How it works — the request pipeline

Order matters, and it is not arbitrary: **reject cheaply before doing expensive work — but never
authorise before you know which object is involved.**

| # | Stage | Rejects | Cost of rejecting here |
|---|---|---|---|
| 1 | TLS termination | Plaintext, bad certificates | Near zero |
| 2 | Edge / DDoS filtering | Volumetric and known-bad traffic | Zero to you — it never arrives |
| 3 | Rate limiting | Floods, brute force, scrapers | Microseconds |
| 4 | **Authentication** | Anonymous and forged callers | One signature check or one cache read |
| 5 | Schema validation | Malformed and oversized bodies | Cheap, and it must precede parsing into your domain types |
| 6 | Function-level authz | Callers who may not use this operation at all | Cheap — this is what a gateway can do |
| 7 | **Load the object** | — | A database read; you are now committed |
| 8 | **Object-level authz** | The caller who may use this operation, but not here | The only place this can be decided |
| 9 | Field-level filtering on output | Fields this caller may not see | Serialise per audience, explicitly |
| 10 | Audit log | Nothing — but it is how you answer "what was taken?" | Write it before you return |

Stages 3 and 4 are frequently ordered the wrong way round on login endpoints, where the expensive
password hash sits *before* the limiter — see [authentication](../authentication/). Stage 8 is
frequently absent. Stage 10 is frequently absent, and its absence is only ever discovered during an
incident, when it is the difference between "we know exactly which 14 records were read" and "we
must notify everyone".

## 13. When to use it

All of it, on anything internet-facing, from the first commit. But if you are ranking by return on
effort:

1. **Object-level authorisation on every endpoint that takes an id.** Nothing else on this page
   comes close.
2. **Parameterised queries everywhere**, enforced by linting.
3. **Rate limiting** on authentication, search, export, and anything that sends a message or costs
   money.
4. **Secrets out of the repository**, with scanning at commit time and a rehearsed rotation.
5. **Deny-by-default routing**, so a new endpoint is unreachable until someone declares a policy.
6. **Audit logging** on reads of sensitive data, not only on writes.

## 14. When NOT to

- **Do not add a policy engine before you have per-object checks.** Sophisticated infrastructure
  around a missing check is expensive theatre.
- Do not build ABAC or ReBAC for a system whose real rule is "users see their own rows". Choose the
  simplest model that expresses the rules you actually have.
- Do not buy a WAF to avoid fixing injection. Fix the injection; keep the WAF for the window before
  a patch ships.
- Do not encrypt fields at the application layer without knowing what threat that addresses — it
  usually breaks querying and protects against a threat model you have not written down.
- Do not put an authorisation check in five places. Put it in one place that cannot be bypassed.
- Do not rely on obscurity: unguessable ids, undocumented endpoints, and a private repository are
  all reconnaissance costs, not controls.

## 17. Trade-offs

| Choose | Get | Pay |
|---|---|---|
| Per-object authorisation | The vulnerability class disappears | A decision on every object, in every list, on every request |
| Central policy service | One place to reason about access; consistency | A hop on every read — then a cache, then a staleness window |
| Scoped queries as the check | Fails closed by construction | Authorisation logic spread through the data layer |
| Strict input allowlists | Whole classes of injection become impossible | Rejects valid-but-unforeseen input; real users hit it |
| Aggressive rate limits | Abuse becomes expensive | False positives on shared IPs, mobile networks, and enterprise NAT |
| Short-lived dynamic secrets | A leak expires on its own | Secret management infrastructure and a dependency on it |
| Detailed audit logs | You can answer "what was taken?" | Storage cost, and the log now holds sensitive data itself |
| Gateway-enforced policy | One consistent place for coarse rules | Encourages services to trust their input, which is the deeper bug |

## 18. Why not?

| Alternative | Why not here | When it WOULD win |
|---|---|---|
| **Gateway-only authorisation** | Cannot see objects; teams then assume it covered them | Coarse route policy, rate limiting, and authentication — genuinely good at those |
| **Database row-level security** (e.g. Postgres RLS) | Policy lives in SQL, away from the code; harder to test and review | Strong and underused — makes bypass genuinely difficult, and enforces it for every client of the database |
| **Policy engine** (OPA, Cedar) | Another service, another cache, another failure mode | Complex rules that change independently of deploys, or an audit requirement for declared policy |
| **Zanzibar-style relationship service** | Substantial infrastructure | Sharing graphs: documents, folders, nested teams. Google Docs-shaped problems. |
| **Framework scopes / ORM defaults** | Silent when someone bypasses the scope | Small teams with strong conventions — fine, if a test enforces it |
| **Trust the internal network** | One foothold is total access; there is no perimeter any more | Genuinely isolated environments with no user-facing surface — rarer than claimed |
| **Nothing — public data** | Only honest when the data is genuinely public | Public read-only content. It belongs in the table; **an options list with no "do nothing" row is unfinished.** |

## 19. Failure scenarios

| Failure | What happens | Mitigation |
|---|---|---|
| **New endpoint ships without an object check** | Silent cross-tenant data exposure, often for months | Deny by default; a test that fails when a route has no declared policy |
| **Policy service unavailable** | Fail open (everyone gets in) or fail closed (nobody works) | Decide in advance; cache last-known-good decisions; fail closed for writes, consider open for reads |
| **Cached decision goes stale** | A revoked share keeps working for the TTL | Short TTL plus explicit invalidation on revoke; state the window |
| **Rate limiter down** | Either everything is limited, or nothing is | Fail open on the limiter but keep a global concurrency cap as a backstop |
| **Mass assignment** | A caller sets `is_admin`, `account_id`, or `price` | Allowlist writable fields; test that unexpected fields are rejected |
| **Secret leaked in a commit** | Live credentials in public history, indexed within minutes | Scan pre-commit and server-side; rotate immediately; rehearse it |
| **SSRF into cloud metadata** | Instance credentials exfiltrated; often full account compromise | Host allowlist, block link-local, require IMDSv2-style protections, re-check after redirects |
| **Verbose error responses** | Stack traces reveal versions, paths, and query structure | Generic errors outward, detail to logs with a correlation id |
| **Enumeration via 404 vs 403** | Existence of records is disclosed by the status code | Return the same status for "not found" and "not yours" on sensitive resources |
| **Audit log missing** | You cannot scope the breach, so you must assume the worst | Log reads of sensitive data, immutably, before responding |

## 25. Without it → With it → New problem → Next

```
Without it   →  authenticated users read and modify each other's records by
                changing an id in a URL, and nothing in the logs looks unusual
With it      →  every object access is checked against the caller, at the point
                the object is loaded, and it fails closed when someone forgets
New problem  →  an authorisation decision on every object, in every list, on
                every request — latency, plus a policy surface that must itself
                be tested and kept correct
Next         →  a policy layer with cached decisions, which reintroduces
                staleness: a revoked share stays live for the length of the TTL
```

That last line is the same trade as [JWT revocation](../jwt/) and the same trade as any
[cache](../../04-caching/fundamentals/). See [the chain](../../SYSTEM-DESIGN-THINKING.md#part-1--the-chain).

## 28. Common mistakes

| Mistake | Why it is wrong |
|---|---|
| **Checking authentication and calling it authorisation** | The bug behind most real API breaches |
| Authorising the route but not the object | A gateway cannot know what invoice 8842 is |
| Trusting UUIDs to protect records | Unguessable is not unauthorised — ids leak through logs, links, and support tickets |
| `update(request.body)` | Mass assignment: the caller picks which columns to write |
| Returning full records and filtering in the front end | The client is not a filter; the data was already sent |
| Client-side validation only | The client runs on the attacker's machine |
| Escaping instead of parameterising | Injection is a context problem, not a character problem |
| Reflecting `Origin` with `Allow-Credentials: true` | Any site can read authenticated responses as your users |
| Believing CORS is an access control | It is a browser policy; nothing else honours it |
| Rate limiting by IP only | NAT punishes real users; attackers rotate addresses |
| Secrets in the repository | Permanent in history; rotate, do not just delete |
| Optimising secret length over rotation speed | The unrotatable key is the actual incident |
| Different responses for "not found" and "not yours" | Free record enumeration |
| No audit trail on reads | You cannot scope a breach, so you must notify everyone |

## 29. Monitoring

**The 403 rate per principal is the most useful security signal an API has, and almost nobody alerts
on it.** A single token producing a burst of authorisation failures across many object ids is
enumeration in progress — someone walking `/orders/1`, `/orders/2`, `/orders/3`. It is unambiguous,
cheap to detect, and it fires while the attack is still happening rather than afterwards.

Alongside it: the *breadth* of distinct object ids touched per principal per hour, which catches
scraping that stays within permissions; authentication failure rate split by reason; rate-limit
rejections by key and endpoint (a sudden drop can mean the limiter broke, not that abuse stopped);
5xx rate on validation paths, which often means someone is fuzzing; outbound requests from services
that should not make any, as an SSRF signal; and secret-scanning hits, which should page rather than
email. Correlate with [observability](../../11-observability/) and keep a correlation id on every
request so an incident is reconstructible.

## 31. Exercises

**1.** Your `/api/invoices/:id` endpoint requires a valid JWT and returns the invoice. A pentester
reports that any authenticated user can read any invoice. A colleague proposes switching invoice ids
from sequential integers to UUIDs. Evaluate.

<details><summary>Answer</summary>

It reduces discovery, not access. Sequential ids let an attacker enumerate the entire table with a
loop; UUIDs mean they need to obtain ids from somewhere else. But "somewhere else" is not exotic:
ids appear in shared links, emails, referrer headers, browser history, exported CSVs, support
tickets, screenshots, third-party analytics, and log aggregators that half the company can read. One
leaked id is one unauthorised read, forever, with no way to detect it as unauthorised.

The actual bug is that authorisation was never checked against the object. The fix is to make the
ownership condition part of how the record is fetched — `current_user.invoices.find(id)`, a policy
call, or a row-level security predicate — so that an invoice belonging to someone else returns
nothing regardless of how the attacker learned its id.

UUIDs remain worth having for other reasons (they do not leak volume, they are safe to generate
client-side, they avoid collisions across shards). Just never let them be described as the fix.
**Unguessable is not unauthorised**, and the sentence is worth using verbatim in the review.
</details>

**2.** A frontend engineer cannot call your API from `app.partner.com`. Under time pressure they
change the server to echo the incoming `Origin` header into `Access-Control-Allow-Origin` and set
`Access-Control-Allow-Credentials: true`. It works. What did they actually build?

<details><summary>Answer</summary>

A universal cross-site read primitive against every logged-in user.

Reflecting `Origin` means *every* origin is allowed, one request at a time — the allowlist is now
"whoever is asking". Adding `Allow-Credentials: true` tells the browser to send cookies and to let
the calling script read the response. So any website a user visits while logged in to yours can
issue authenticated requests as them and read the results: profile, invoices, tokens, everything the
session can reach. No XSS on your domain is needed. The victim only has to visit a page.

This is strictly worse than the CSRF it resembles, because CSRF can normally only *write* blind — the
attacker triggers an action without seeing the response. This configuration hands over the response
body too.

The correct fix is an explicit allowlist of known origins, compared exactly (`https://app.partner.com`,
not a `startsWith` or a regex with an unescaped dot), with credentials permitted only for those. And
the framing worth carrying away: CORS was never protecting your server, so a CORS change is not a
server-hardening change — it is a decision about which *other people's pages* may read your
authenticated responses.
</details>

**3.** A dashboard shows an authenticated user's 403 rate jumping from 2 per hour to 4,000 per hour,
across thousands of distinct object ids, all returning 403. Your object-level authorisation is
working correctly. Is there an incident?

<details><summary>Answer</summary>

Yes — and it is a good one to catch, because the controls held.

Every request being denied means authorisation is doing its job. But the pattern is unambiguous:
someone is walking the id space with a valid credential. Two possibilities, and both need action.
Either a legitimate user's token has been stolen and the thief is mapping what it can reach, or the
account itself is hostile. The distinguishing evidence is elsewhere: source IP and ASN change,
user-agent, time of day, and whether normal activity from that account continues in parallel.

Act now rather than after: rate-limit or suspend the credential, capture the full request log before
retention expires, and check for any object ids that returned **200** in the same window — those are
the ones that were actually reachable, and they are your exposure list.

The general lesson is the one in §29. **Denied requests are the signal; most teams only alert on
errors and successes.** A 403 spike is one of very few security signals that fires during the attack
rather than during the post-mortem, costs nothing to collect, and has almost no false-positive
problem — legitimate clients do not generate thousands of authorisation failures across thousands of
distinct ids.
</details>

**4.** An AWS access key is committed to a private repository, spotted by a scanner four minutes
later, and the commit is reverted and force-pushed within ten. The engineer marks the ticket
resolved. What is still wrong?

<details><summary>Answer</summary>

The key is still live, and it is still in history.

A force-push rewrites the branch pointer; it does not reliably destroy the object. The blob remains
in every clone anyone has already taken, in the reflog, in any fork, in CI caches, in the code
review tool's stored diff, and — if the platform ever surfaced it via an API — in whatever indexed
it. Private repositories are also not a boundary: contributors leave, access is broad, and repos get
made public by accident. Treat exposure as complete from the moment of the push.

The only action that resolves this is **rotation**: issue a new credential, deploy it, revoke the
old one, and then check CloudTrail (or the equivalent) for any use of the old key between commit and
revocation. Revocation is what ends the incident; deletion of the line is cosmetic.

The interesting follow-up is the timing. Four minutes to detect is good. The question nobody asked
is **how long rotation takes** — if that key is referenced by nine services and rotating it needs a
coordinated release, the exposure window is measured in days regardless of how fast the scanner was.
That is the real finding: rotation speed, not secret strength, is the property that bounds the
damage, and it is the one that is almost never tested until it is needed.
</details>
